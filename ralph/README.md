# The loop: spec-driven development + Ralph

**Specs are truth, the plan is disposable, one task per fresh context, tests are backpressure.** The trusted Ralph fallback runs three fresh CLI processes serially at three model tiers:

| Stage | Tier | Prompt | Role | Claude Code | Codex CLI |
|---|---|---|---|---|---|
| build | worker | `PROMPT_build.md` | owner named by the task (`g2-glasses-dev` / `relay-backend-dev` / `spotter-pwa-dev`) | Sonnet 5 @ high | GPT 5.6 Terra @ high |
| review | reviewer | `PROMPT_review.md` | `protocol-keeper` (protocol/relay diffs) or `hud-qa` | Opus 5 @ high | GPT Sol 5.6 @ high |
| replan | planner | `PROMPT_replan.md` | `plan-updater` | Opus 5 @ xhigh | GPT Sol 5.6 @ xhigh |
| audit (human-invoked, outside the loop) | auditor | — | Fable 5.1 as final QA over a batch; writes `docs/reviews/<date>-*.md` | Fable 5.1 / Opus 5 @ xhigh | GPT 5.6 Sol @ xhigh |

Routing lives in `ralph/models.env`; `npm run sync:agents` pushes it into `.claude/agents/*.md` and `.codex/agents/*.toml`. Role prompts never mention a model.

## Files

```
specs/000-constitution.md   invariants + process rules (read every iteration)
specs/0X0-*.md              what "done" means: requirements + acceptance criteria (AC-n), [HW] = human
IMPLEMENTATION_PLAN.md      disposable, ordered task list; first unchecked task under "## Next" is next
ralph/PROGRESS.md           history + "Blocked on human"
ralph/last-build.md         worker → reviewer/planner hand-off (git-ignored; cleared at the start of every iteration)
ralph/last-review.md        reviewer → planner hand-off (git-ignored); PROGRESS.md is the committed record
HANDOFF.md                  tracked cross-instance snapshot; specs/plan/progress remain authoritative
ralph/loop.sh               the loop (bash); ralph/models.env config; ralph/logs/ transcripts
ralph/STOP                  create to stop after the current iteration; ralph/DONE written by the planner
agents/roles/*.md           canonical role prompts (edit these)
.agents/skills/*/SKILL.md   canonical project skills (edit these)  → mirrored to .claude/skills
.claude/agents, .codex/agents   GENERATED by scripts/sync-agents.mjs — never hand-edit
AGENTS.md                   operational guide loaded by Codex natively and by Claude via CLAUDE.md
```

The ignored `ralph/last-build.md`, `ralph/last-review.md`, and `ralph/.last-message.md` are ephemeral stage transport and may be stale between interactive sessions. A fresh agent uses `HANDOFF.md` plus committed `IMPLEMENTATION_PLAN.md` and `ralph/PROGRESS.md`, not an ignored transport file, to establish current state.

## Running it

Prerequisites: Node 22, git, and either `claude` (Claude Code CLI) or `codex` on PATH, logged in. Work from a **local clone** — do not run the loop inside the OneDrive-synced folder (file locking, sync churn on `node_modules` and `.git`). On Windows use Git Bash or WSL.

```bash
node scripts/sync-agents.mjs            # after any edit to roles/skills/models.env
ralph/loop.sh plan                      # first time, or to regenerate the plan from specs
ralph/loop.sh once                      # one build → review → replan cycle; read ralph/logs/
ralph/loop.sh                           # run until DONE / STOP / MAX_ITERATIONS
RUNNER=codex ralph/loop.sh              # same loop on GPT
RALPH_UNATTENDED=0 ralph/loop.sh once   # Claude asks before edits/commands (default is skip-permissions: use a VM/sandbox)
```

Stop it: `touch ralph/STOP` (checked at the start of each iteration, so the current build→review→replan cycle finishes first; delete the file to resume). Watch it: `tail -f ralph/logs/*.log`. Steer it: edit a spec (add a Decision, answer an Open question) and run `ralph/loop.sh plan`. Iteration numbers come from the last row of `ralph/PROGRESS.md`, so they stay continuous across clones and Claude↔Codex hand-offs.

## Interactive parallel streams

The parent agent may accelerate independent plan tasks with subagents. This is a coordinator workflow, not a mode of `ralph/loop.sh`:

1. The planner marks tasks with stream metadata and non-overlapping write scopes. Before dispatch, the coordinator creates one Git worktree per stream and records the lease id, exact base commit, task id, dependency gate, write scope, and exclusive lock(s).
2. The coordinator prepends that lease block to `PROMPT_build.md`. The exact leased task replaces “first unchecked” for that worker only. The worker still gets one fresh context, changes one task inside its scope, reaches green backpressure, makes one commit, and exits.
3. A fresh reviewer in the same worktree receives the lease base and worker head, applies `PROMPT_review.md`, and reviews exactly `base..head`. It writes only that stream's ignored `ralph/last-review.md`.
4. The coordinator integrates only `approve` / `approve with nits` commits, one at a time in declared dependency order. After each integration it runs `npm run typecheck`, `npm test`, and `npm run lint` at the root. A failed integration gate is not advanced or hidden by another stream.
5. A fresh `plan-updater` reconciles each integrated result serially and is the only agent that writes specs, `IMPLEMENTATION_PLAN.md`, or `ralph/PROGRESS.md`. Review-blocked work is replanned before it is leased again.

Scopes that overlap, tasks sharing an exclusive lock, `[HW]` work, and tasks whose dependency gate has not opened never run concurrently. A stream may begin implementation while waiting for an integration dependency, but it may not make its final commit until its worktree contains that dependency and the full gates are green.

## Verify before first run (CLI facts this loop assumes — confirm against `claude --help` / `codex exec --help` on your install)

The prompts, specs and role files are runtime-independent; only `loop.sh` and the generated agent files depend on CLI details, and CLIs change fast. Check once:

- Claude Code: `claude -p --agent <name>` runs a `.claude/agents/<name>.md` as the main agent in print mode; `--effort` accepts `high` / `xhigh`; `effort:` and `skills:` are honoured as subagent frontmatter keys; `@agent-<name>` mentions work interactively. If `--agent` is not available, set `RALPH_CLAUDE_USE_AGENT=0` — the loop then prepends the role file to the prompt and passes `--model/--effort` explicitly.
- Codex CLI: `codex exec -` reads the prompt from stdin; `--ask-for-approval never` and `--sandbox workspace-write` are accepted by `exec`; `-c model_reasoning_effort="xhigh"` is accepted for the chosen model (the loop retries with `high` if the error mentions reasoning); the `CODEX_*_MODEL` ids in `models.env` are real model ids on your account. For parent-spawned subagents: `.codex/agents/*.toml` with `developer_instructions` / `model_reasoning_effort` / `sandbox_mode`, `[features] multi_agent = true` in `~/.codex/config.toml`, and the project marked trusted. The loop itself does not need multi-agent mode.
- Plugin skill names may be namespaced in Claude Code (`/everything-evenhub:sdk-reference`); the `codex plugin marketplace add` command is what the plugin README documents.

## Hand-off between Claude and GPT

Everything an agent needs is in plain markdown in the repo; nothing lives in a chat history. On a cross-instance handoff, read `HANDOFF.md` first for the local snapshot, then verify it against the specs, plan, and progress log. To move from Claude to Codex mid-project: set `RUNNER=codex`, confirm the `CODEX_*_MODEL` ids in `models.env`, run `node scripts/sync-agents.mjs`, and continue — the same plan, specs, and progress log carry over. Codex reads `AGENTS.md` and `.agents/skills` natively and gets the roles as `.codex/agents/*.toml` (enable `[features] multi_agent = true` in `~/.codex/config.toml` and mark the project trusted if you want the parent to spawn them). The SDK plugin `even-realities/everything-evenhub` is published for both Claude Code and Codex.

## What a human does

- `[HW]` tasks under *Needs human* (glasses, phones, Cloudflare account). Do them, put the evidence file the spec names in `qa/<date>/` (or mark the item done under "Blocked on human" in `ralph/PROGRESS.md`), then rerun `ralph/loop.sh plan` — the planner recognises either; a ticked box in the plan itself is lost on regeneration.
- `[SIM]` tasks parked under *Needs simulator* (the loop's machine could not launch the Even Hub simulator): on a machine that has it, run `npm run sim:scenarios`, commit `qa/<date>/sim/`, rerun `ralph/loop.sh plan`. Simulator evidence is functional proof only; it never closes an `[HW]` item.
- Answer *Open questions* in specs; relax an acceptance criterion if it is wrong (agents may only mark it `DISPUTED`).
- Read `ralph/last-review.md` occasionally. Repeated `block`s on the same area mean a spec is ambiguous — fix the spec, not the worker.

## Why three tiers

Workers do the most tokens and the least judgement — cheapest model at high effort. Reviewers must catch a placeholder test or an invariant breach in one pass — stronger model, high effort, read-mostly. The planner's mistakes are multiplied by every iteration that follows, and it runs once per cycle with a small input — strongest model at x-high effort is the cheapest place to spend reasoning.
