# Spotter console conventions

The spotter is standing outside, glancing between the track and the phone, often with one hand. Design for sunlight, gloves, and zero attention to spare.

## Screens

1. **Join** (Maxx, 2026-09-25 design round 4: "When a user goes to the page, they are assigned a random room ID. User is asked to set a 4 digit pin."):
   - **New visit** (no stored room, or the stored one was last heard more than `ROOM_TTL_MS` = 24 h ago): a random 6-char `[A-Z0-9]` code (`generateRoomCode`, `crypto.getRandomValues`, no modulo bias) shown large, a required **Set a PIN** field (4 digits), an optional name, and **Start**. If the relay answers `auth` to a fresh code (it collided with someone else's PIN'd room), `main.ts` silently tries **one** new code; a second `auth` goes back to Join with the wrong-PIN notice.
   - **Join an existing room** (a link under Start): the classic form — room code (auto-uppercase, 4–6 chars), PIN (optional), name, "Join as spotter" — for a second spotter phone. "Start a new room" goes back.
   - Room/PIN/name persist in `localStorage` (`g2rs:v1:*`); `g2rs:v1:seenAt` records when the phone last heard its room, so a return inside 24 h auto-joins. The relay host is in small print so a wrong deployment is obvious. Both sections are always rendered and toggled with `hidden`.
2. **Console** — the only screen that matters. **It never scrolls** (Maxx, 2026-09-04 design round 2): a `100dvh` grid (with a `100vh` fallback first) with `overflow: hidden` and safe-area insets. Design round 4 (2026-09-25): "This can all fit on the top half of the app ui … On the bottom half, have buttons to send messages to driver."
   - **Header — one 36 px row of small icons** (no full-width bars): the room code as a small mono chip (a button whose hit box is still 44 px, hanging transparently over the row's edges; tap → the **driver setup screen**, see below, tap again to close); the **link dot** (green when the socket is open *and* the room replayed, red otherwise) with a small red **`RECONNECTING`** pill beside it while down (`SYNCING…` while open but not yet replayed); the **driver dot** (green online / grey offline); the **ack icon** (`⌛` while the room's message is unacknowledged, `✓` once `ackedAt` is set, hidden when there is no message); latency `123 ms` on the right.
   - **Layout as of 2026-10-28 (design round 7 + 7b; round 6's approved mock is `docs/reviews/spotter-round6.png`, round 7b's built console `docs/reviews/spotter-round7.png`)** — portrait, top to bottom: header 36 · body padding 8 · lanes · **12 px air** · faders · **12 px air** · two corner-call rows (each an 18 px `ENTRY` / `EXIT` heading, 4 px, 44 px buttons; 16 px between the rows) · **12 px air** · one row of built-in messages (44 px) · free space (≥ 12 px) · input + Send · padding 8. The console body has 8 px side padding; `--air: 12px` (20 px in round 6), `--lane` (a lane's width) and `--lane-h` (its height) are custom properties on `.console__body`.
   - **Top part** (fixed height; ends at ≤ 55 % of a portrait screen — the CSS aims at 54 %; design round 5 loosened round 4's "top half" so the faders get a usable travel):
     - **Lane row**: three **equal rounded buttons** (squares where there is room, never taller than wide — round 7) side by side in glasses order, **left to right ◀ · ▲ · ▶ (BOTTOM · MIDDLE · TOP)** ("Bottom is the left most buttons, Middle is middle, and top is right"; the glyphs match the glasses' lane icons since design round 5, and ◀/▶ carry U+FE0E so iOS draws them as text, not emoji). Round 6: **glyph only** (40 px; the lane name is the button's `aria-label`), `border-radius: 18px`, 10 px gaps, filling the row (width `--lane` = `min((100vw − 36px) / 3, 140px)`: 118 px at 390 wide, 108 px at 360; a wider screen centres capped buttons). Round 7: height `--lane-h` = `min(var(--lane), max(64px, (100dvh − 416px) / 2))` — square where there is room; on a short portrait screen the lanes and the fader travel split what the rest of the console leaves (416 px since round 7b) half and half. Since round 7b the lanes are squares again at 390×664 and 360×640 (only a shorter screen makes them give way); in landscape `--lane-h` = `--lane` (squares). **No CLEAR button**: tapping the lit lane again sends `lane: null` (`laneTap` in `intents.ts`). Selected = solid bright fill with dark glyph; unselected = dark fill with bright glyph and a 2 px border.
     - **Car faders** (Maxx, 2026-09-30 design round 5: "Let's go back to using a slider … Change names to inside behind outside use some x axis spacing between the 3 items … basic slider with a button kinda like what you see on audio recording/dj devices"): three **vertical faders** side by side, `INSIDE` / `BEHIND` / `OUTSIDE` (= `cars[0]`, `[1]`, `[2]`, the glasses' left-to-right order), each on its own panel with an 18 px gap between panels. The whole **panel** (`data-act="fader"`, `touch-action: none`) is the pointer target, so a thumb in the band above detent 3, below detent 0 or on the label still moves the knob; the finger is measured against the inner `role="slider"` **track** (the panel width, ≥ 44 px), which has a dark slot, **four detent marks** `3 · 2 · 1 · 0` top to bottom (0 = no car at the bottom, 3 = on the bumper on top; the mark at the level is lit), an accent **fill** from the bottom to the knob, and a **knob** — a 64 × 44 px rounded rectangle with a centre line, like a mixer fader cap. The track box is the knob's travel: detent n sits at n/3 of it and the knob overhangs it by half its height, which the track's margins leave room for. Travel height `--track` = `clamp(96px, min(54dvh − 128px − var(--lane-h), 100dvh − 416px − var(--lane-h)), 200px)` portrait — the smaller of the 54 % budget (128 px = header, padding, air and panel chrome) and what the rows below leave (416 px = everything on the screen but the lanes and the travel, 4 px of slack included; round 7b) — 110 px at 360×640, 113 px at 390×664 (the 54 % budget binds); `clamp(96px, 100dvh − 144px − var(--lane), 200px)` landscape. A fader at level 3 turns red (panel border, fill, knob line) like the glasses' alert outline. The knob's position is the `--pos` custom property (0..1) on the track's `style`.
   - **Bottom part**:
     - **Corner calls** (Maxx, 2026-10-28 design round 7): two rows, **ENTRY** over **EXIT**, each a **heading line above the row** with the phase name (round 7b: 15 px extra-bold, 18 px line, **pure white `#fff`**, left-aligned, `aria-hidden`; the row is a `role="group"` labelled with the phase — Maxx moved it from the mock's left column to above the row the same day) then `GO LOW · GO MID · GO TOP` left to right across the **full width** (LOW left → TOP right, the lanes' order), three equal columns shared by both rows, **16 px** column gap, 4 px under the heading, **16 px** between the rows (round 7b: "more spacing"), 44 px tall. Same family as the built-ins (`class="say say--call"`, amber outline, `data-act="say"`); accessible names `ENTRY GO LOW` … `EXIT GO TOP`. A tap sends **one** `msg` whose text is the action, `'\n'`, the phase — `callMessage(action, phase)` in `intents.ts` → `'GO LOW\nEXIT'` — which the glasses draw as two lines and flash like any message. Client constants `CALL_PHASES` / `CALL_ACTIONS`. No lit state (the built-ins have none either).
     - **Built-in messages** (design round 6, 2026-10-01; rounds 7 and 7b): **one row of two** — `LEADERS BEHIND · PITS` (client constants `BUILTIN_MESSAGES`, left to right; round 6's 2×2 renamed PULL OFF → EXIT and removed SPIN, round 7 renamed EXIT → PITS because EXIT is now a corner phase, round 7b removed CATCHING UP and PULLING AWAY). Two **equal** amber-outlined buttons, 44 px tall (56 in round 6), 10 px apart, one colour (no alert variant). One tap sends that `msg`.
     - **Message row**, pinned to the bottom: `[type a short message] [Send]` — input maxlength 80; Send (primary, ≥ 92 px wide) sends `msg` and clears the input. There is no Clear button (the glasses auto-ack and the relay's 6 s stale clear retire a message).
     - **No saved messages on the page** (round 6): the Save button and the preset chips are gone. The protocol's `preset` messages, `RoomClient` and the relay's `State.presets` storage are untouched and may come back to the page later; the spotter neither shows nor sends them.
   - Bottom safe area padded; the update toast is the last grid row and costs nothing while hidden.

**Driver setup screen** (T058, Maxx 2026-09-30 — hosted deploy + QR hand-off): the room-chip overlay, full screen, tap anywhere to close. Top to bottom: `ROOM`, the code large (accent, mono), `PIN 1234` (or `no PIN`), a **QR code** (inline `<svg>`, black on a white quiet zone, `min(64vw, 38dvh, 320px)` square) of `https://<relay>/glasses/?room=<ROOM>&pin=<PIN>&name=driver` (`glassesUrl` in `net/room-client.ts`: the relay origin with `ws`→`http`, `pin=` always present so an old stored PIN is cleared), that URL as small selectable mono text, and three lines: "Driver: Even app → Developer Mode → Scan → aim at this code." / "The glasses join this room automatically." / "Tap anywhere to close." In landscape the QR sits left of the text. The QR comes from `ui/qr.ts`, a vendored MIT encoder (Project Nayuki port, level M, versions 1–10, byte mode) memoised per URL; `vdom.ts` creates `<svg>` subtrees with `createElementNS`. `view.test.ts` asserts the `<svg>`, its path = `qrPath(encodeQr(url))` and the exact URL text; `qr.test.ts` pins the encoder to Nayuki's reference `qrcodegen` 1.8.0; `layout.test.ts` checks the screen fits all three viewports with the QR ≥ 140 px.

Landscape (`orientation: landscape` and height ≤ 560 px): the top half on the left (48 %), the messages on the right (corner calls, then the built-in row, at the top; input + Send at the bottom — 264 px of the 308 px a 360 px tall screen leaves). The lanes stay squares there. The lanes fill the left half's row (`--lane` = `min((48vw − 27.68px) / 3, 100dvh − 240px, 140px)` — they give way on a short screen so the faders keep 96 px of travel) and the faders take the height left. Every button the spotter can hit stays ≥ 44 px, lanes ≥ 64 px.

`apps/spotter/test/layout.test.ts` is what holds this: it builds the app, serves `dist`, and measures 390×664, 360×640 and 740×360 in a real Chromium (`playwright-core`, pinned, `PLAYWRIGHT_BROWSERS_PATH`), each twice: relay down (pill up) and a live room replayed by an in-page fake WebSocket with a lit lane, an unacknowledged message and three saved messages (which must not appear). Change a row height and re-run it before changing the numbers above (`G2RS_LAYOUT_SHOTS=<dir>` saves a screenshot per console and viewport). Round 7b measured (2026-10-28; the live room's message is the two-line `'GO LOW\nEXIT'`): no scroll anywhere, 13 buttons (room chip, 3 lanes, 6 corner calls, 2 messages, Send) all ≥ 44 px and no Save/preset controls, the lanes larger than every other button and never taller than wide (round 6 asserted squares; they are squares again here), lanes 118 × 118 at 390×664, 108 × 108 at 360×640, 109 × 109 at 740×360, 12 px of air lanes → faders and faders → corner calls (asserted ≥ 10; round 6 had 20, asserted ≥ 18), faders ending at y = 359 at 390×664 and 346 at 360×640 (54.0 %), 18 px fader gaps, knob 64 × 44, travel 113 / 110 / 107 px, corner calls 114 × 44 / 104 × 44 / 111 × 44 in three shared full-width columns, 16 px between the buttons and from the ENTRY buttons to the EXIT heading (asserted ≥ 15), white ≥ 15 px ENTRY / EXIT headings above each row, the two built-ins one size in one row (182 × 44 at 390 wide, 167 × 44 at 360, 177 × 44 in landscape).

## Behaviour

- Lane tap → `lane` immediately; button reflects *server* state from the next `state` frame (optimistic highlight allowed for ≤ 300 ms, then reconcile). Tapping the lit lane (as the console shows it, optimistic highlight included) sends `lane: null` — the round-6 replacement for the CLEAR button (`laneTap(selected, tapped)` in `intents.ts`; `main-lane.test.ts` drives it through `main.ts`).
- Car fader → exactly one `cars` frame per gesture, carrying the **full triple** with only that fader changed. `pointerdown` anywhere on a fader's panel captures the pointer (`setPointerCapture`), reads the inner track's box once, and puts the knob under the finger; `pointermove` drags the knob live (`model.dragKnob` = the finger's 0..1 position; `model.dragCars` = the nearest detent, which the marks, fill colour and `aria-valuenow` show); nothing is sent while the finger is down; `pointerup` — and `pointercancel`, which commits the detent the knob was showing rather than silently reverting it — snaps the knob to the nearest detent and sends once if the level changed. A **tap** is a gesture that never moves: the knob jumps to the detent under the finger and that is sent. Releasing on the level the fader already had sends nothing (a fader has its own 0 detent; the round-3/4 "tap the lit top clears" rule is gone). A second finger is ignored while one fader is held. Keyboard: the focused track steps with ↑/→ and ↓/←, Home = 0, End = 3, one send per change. `faderPosition` / `detentAt(position)` (the one snap rule) / `detentFromPointer(y, trackTop, trackHeight)` / `startCarDrag` / `moveCarDrag` / `endCarDrag` / `nextCars` in `intents.ts` are that decision, kept pure so they are unit-tested without a DOM; `main-fader.test.ts` drives the real `main.ts` with synthetic pointer events. A gesture starts from `selectedCars(model)` (drag → optimistic within 300 ms → the room), so two quick changes on different faders compose. No throttle.
- Messages: a built-in button sends its text as `msg` (a corner call its two-line `action\nphase` text); Send (or Enter in the input) sends the trimmed, 80-capped input and clears it. `normaliseMessage` trims the ends only — never strip or collapse an inner `'\n'`. Nothing on the page sends `preset` (round 6). The console never prints the room's message text (the header's ack icon is its only trace), so a `'\n'` in it needs no rendering on the phone; if a future row shows it, render the break as a space or a line break, never as a literal `\n`.
- Reconnect: handled by the shared `RoomClient` — on `open` it sends `hello`, takes the replayed `state` as truth, then flushes only intents queued *while the socket was down* (latest `lane`, latest `cars` triple, any `msg`/`clear`/`preset` in order). Car changes made before the session has replayed are **not** sent as a triple built from the pre-drop local copy: `main.ts` holds the changed faders and, on the first `state` of the session, sends `rebaseCars(state.cars, pendingRows)` — only those faders override the replayed room, so faders the relay cleared meanwhile (the 6 s stale clear) do not come back. Never re-send an already-delivered `msg` (each `msg` gets a new id and would duplicate). The pill stays up until the first `state` arrives, then the UI reconciles to it. **Foreground (T065):** the page disconnects on `visibilitychange` → hidden (a throttled hidden tab would stop pinging, be reaped by the relay and rejoin about once a minute, flapping the driver's `S`), and on visible / `online` / bfcache `pageshow` calls `client.connect(roomUrl(…))`, which reconnects at once unless the socket has heard from the relay within `SOCKET_SILENT_MS - PING_INTERVAL_MS` (`main-resume.test.ts`).
- Latency: round trip from the `ping`/`pong` pair (`pong.ts` field is the client's send timestamp), EWMA over 5 samples, shown in the header; grey out if older than 10 s.
- Haptics: `navigator.vibrate?.(10)` on lane tap, fader down and each detent crossed, and message send (Android only; harmless elsewhere).

## Visual system

- Dark background `#0b0f14`, text `#e8f0f2`, accent `#39ff88` (matches the glasses' green), alert `#ff4d4d`, amber `#ffb020`. Minimum contrast 7:1 for text on buttons.
- Typography: system UI font, 18 px base; lane glyphs 40 px (no label); fader labels 12 px bold, detent numbers 11 px bold; corner-call phase headings 15 px extra-bold white; built-in messages and corner calls 15 px bold, line-height 1.15; the room code chip, overlay and join code in a monospace face. Type sizes are part of the fit — shrink a row before you let a lane drop under 64 px or the faders spill past 55 % of a portrait screen.
- `touch-action: manipulation` globally; `user-select: none` on controls; no hover-only states; focus rings visible for keyboard users anyway.
- No animations longer than 150 ms (the knob eases 90 ms onto its detent, and not at all while held); nothing moves while the spotter is not touching it, except the status header text and a knob following the room's state.

## PWA

- `manifest.webmanifest`: `display: standalone`, `orientation: any`, `theme_color` = background, 192/512 icons (simple ▲●▼ mark on dark), `start_url: /`.
- Service worker: precache the built shell (`index.html`, JS, CSS, icons) with a version stamp; network-first for `index.html`; **never** intercept `/room/*`, `/health`, WebSocket traffic, or `/glasses` / `/glasses/*` (the relay-hosted glasses app — a driver opening its URL on a phone that runs the spotter must never get the cached spotter shell). Show a small "update available — reload" toast when a new SW activates.
- First-visit hint: "Add to Home Screen for full-screen use" with platform-specific one-liners (iOS: Share → Add to Home Screen).
- `<meta name="viewport" content="width=device-width, initial-scale=1, viewport-fit=cover, maximum-scale=1">`.

## Structure (apps/spotter/src)

```
main.ts             bootstrap, the delegated click/input/keydown/pointer listeners, all sends, the join flow
model.ts            Model (+ dragCars/dragKnob) + selectedLane/selectedCars (drag → optimistic → server)
intents.ts          pure decisions: CAR_ROWS/CAR_DETENTS, BUILTIN_MESSAGES, CALL_PHASES/CALL_ACTIONS,
                    callMessage, laneTap, faderPosition,
                    detentFromPointer, nextCars, startCarDrag/moveCarDrag/endCarDrag,
                    rebaseCars, normaliseMessage
join.ts             generateRoomCode, isStartPin, isSessionCurrent (24 h)
storage.ts          join form + seenAt in localStorage
net/room-client.ts  thin wrapper: `new RoomClient({ WebSocket: window.WebSocket, ... })` + latency tee; roomUrl, glassesUrl
ui/vdom.ts          ~170-line positional diff (no framework — AC-5's 40 KB budget); SVG namespace aware
ui/qr.ts            vendored QR encoder (MIT, Project Nayuki port) → one SVG path
ui/view.ts          join + console as one pure function of the Model
sw.ts               service worker
styles.css
```

Keep `view()` pure enough to unit-test with jsdom: given a `State` and a connection status, assert which lane is lit and where each fader's knob sits, the header icons, the pill, and the message buttons. Every interaction is a `data-act` attribute; no handler lives in the tree. Slots are always rendered and toggled with `hidden` so the positional diff never re-creates a control mid-interaction — keep child counts constant.
